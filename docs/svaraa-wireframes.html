Setup link: how it’s generated and what it carries

The link on screen D4 is only a pointer. It carries one random token and no personal data. Everything else stays on the server and is revealed only after the wearer proves she is the right person.

Inside the link

https://svaraa.ai/j/Xk3p9QwR…

A random token of at least 128 bits, generated on the server. Nothing else: no name, no phone number, no health data, no internal IDs. Messaging apps log and preview URLs, so the URL must be safe to leak.

Stored on the server

Only the hash of the token, plus: circle, who created it, purpose (wearer setup and consent), the phone number it is bound to, expiry (suggested 72 h), status (pending, opened, consented, expired, revoked), max uses = 1, the claimed device, an attempt counter.

Revealed in stages

Before sign-in: only “Meera set up Svaraa for you”. After OTP matches the bound number: Asha’s details, contacts and what Meera will see. After she agrees: the circle becomes Pending pairing.

Step by step
  1. The caregiver taps Send link on D4. The app asks the server to create an invite for this circle. The server checks the caller is the owner or an Admin, revokes any earlier open link for the circle, creates the token and returns the URL.
  2. The app drops the pre-written message and URL into the phone’s share sheet (WhatsApp, SMS and so on). In v0 Svaraa doesn’t send it itself; a server-sent SMS could come later.
  3. Asha taps the link. If the app is installed it opens straight to D6. If not, she lands on the store page, and the token is restored after install (deferred deep link). As a fallback the landing page shows a short code she can type in.
  4. The app asks the server what the token is. The server answers with only the caregiver’s first name and the link’s status, and rate-limits these lookups.
  5. Asha signs in with an OTP. The server checks her verified number equals the number the link is bound to. If not: “This link was sent to a different number.” A forwarded link is useless to anyone else.
  6. The server now returns the circle summary for D7. When Asha agrees, the app sends the consent with the token and consent-text version. The server records it, marks the link used and notifies the caregiver. Later steps (pairing, drill) run on her signed-in session, not on the link.
Properties this gives you

Unguessable. Single-use. Short-lived. Bound to one phone number. Revoked automatically on resend, on a number change, or when the owner cancels. “I don’t know Meera” on D6 also kills it. Every step is logged for support.

Device claim: what I suggest

You asked how BLE watches and earbuds handle this. Mainstream consumer devices combine four ideas, and I’d use all four, layered. I’m describing common industry patterns from general knowledge, not any one vendor’s exact implementation, so have your hardware team confirm what the pendant can support.

1Physical possession

Earbuds and watches only become pairable after a physical action: hold a button, open the case, put them in pairing mode. Someone who only has a photo of the box can’t do that.

2Cloud ownership lock

Once paired, the device’s ID is bound to one account in the cloud (the idea behind Apple’s Activation Lock and account-bound watches). A factory reset doesn’t release it; the owner has to.

3Code or QR from the box

Smart-home standards such as Matter use a setup QR or code to identify the product and give a one-time secret. It speeds setup and enables remote claiming.

4Device authenticity

Better devices carry a per-unit key set at the factory. The cloud sends a random challenge and the device signs it, so a copied serial number or QR can’t impersonate a real unit.

Unverified claims can be overridden

If the legitimate buyer finds the device already claimed, they can reclaim it by proving physical possession (press the dot during pairing) plus a support check. A verified claim can’t be overridden this way. This closes the “someone photographed the box” hole.

Verified claims are locked

Anyone else scanning gets screen E5. Factory reset (hold the dot 10 s on the puck) does not release ownership; the owner releases in the app, or support verifies a second-hand sale.

Abuse limits

Rate-limit claim attempts per account and per device. Mask the owner’s identity in error messages. Log every claim, transfer and release for support.

Pairing without a screen

With no display on the pendant, the usual “confirm this code on both devices” step can’t exist. Basic Bluetooth pairing without a code protects less against someone nearby intercepting it, so trust has to come from elsewhere. Options:

1 · Plain pairing + app-layer check (v0 baseline)

The OS shows a simple Pair prompt. Trust comes from the button press that opens a short window, plus the silent signed-challenge from the pendant, plus encryption keys the app and cloud set up on top of Bluetooth. Needs no extra user step.

2 · Out-of-band key (stronger)

A secret per pendant, from the box QR or delivered by the cloud to the wearer’s phone after the claim, is used to authenticate the pairing. Protects against interception without a screen. Needs firmware support.

3 · Spoken code

The pendant speaks a short code (“seven four two”) and the wearer types it. Works with no screen but adds a step that older users may find hard.

I’d ship option 1 and plan option 2 as the upgrade, but this depends on what the pendant’s Bluetooth chip and firmware support, so please confirm with the hardware team.
